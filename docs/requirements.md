# Requirements

What Sketchy is required to do, what it is required *not* to do, and where each
requirement is implemented and proven. Requirements are numbered so they can be cited
from issues, PRs, and code comments.

Companion documents: [`architecture.md`](architecture.md) ·
[`wire-protocol.md`](wire-protocol.md) · [`database.md`](database.md) ·
[`../GLOSSARY.md`](../GLOSSARY.md)

**How to read this.** `MUST` is a hard requirement — breaking it is a bug. `MUST NOT`
is a deliberate non-goal or a safety boundary; adding the behaviour is a product
decision, not a fix. Where a requirement encodes a *reason* rather than only a rule, the
reason is stated, because that is what tells you whether a change violates it.

## Product statement

Sketchy is a self-hosted, online multiplayer drawing-and-guessing game
(iSketch/Pictionary-style), built for "friends playing together" scale. One player
draws a prompt while everyone else races to guess it in the chat. Accounts are optional
for play.

**Scale target (v1):** 50 simultaneous active rooms and 400 connected player seats on
one worker. This is a *validation target* on a documented reference environment, not a
claim that an arbitrary host will sustain it. It is validated by the release load gate,
[`benchmarks/run_load.sh`](../benchmarks/run_load.sh) (#461, R-PLAT-18), whose last
result is recorded here so the target is a measurement rather than a sentence:

[`db/models.py`](../backend/app/db/models.py), [`tests/test_lifecycle_constraints.py`](../backend/tests/test_lifecycle_constraints.py) |

[`deployment.py`](../backend/app/deployment.py) |
| **R-PLAT-12** | `GET /api/ready` MUST test the dependencies this process needs to serve: a bounded, briefly cached database round-trip, and the supervised background loops. [`services/readiness.py`](../backend/app/services/readiness.py) |
| **R-PLAT-19** | Production MUST speak HTTPS only. With `SKETCHY_ENV=production`, startup MUST refuse a `PUBLIC_BASE_URL` that is not an `https` origin (a plain scheme, a loopback name, a path): every mailed link is built on it and every plain request is sent to it. A request arriving over plain HTTP MUST be redirected with 308 to the same path on that origin — its method kept, so a POST is not turned into a GET — and a plain WebSocket handshake MUST be closed before it is accepted; only `/api/health`, `/api/ready` and `/metrics`, which an orchestrator reaches on the process's own port, MUST answer plain. Every production response MUST carry `Strict-Transport-Security` with a one-year lifetime. The scheme judged MUST be the one uvicorn established from a trusted proxy (R-PLAT-10), never a raw forwarded header: behind a proxy the deployment did not name, the result is a redirect loop on the first page load, which is the loud failure preferred over a year-long cookie issued across a hop somebody could read (#467). [`security_headers.py`](../backend/app/security_headers.py), [`deployment.py`](../backend/app/deployment.py) |
| **R-PLAT-20** | Every response, in every environment, MUST carry the browser hardening headers: a `Content-Security-Policy` that admits only this origin — the built shell's inline script by a hash computed from `frontend/dist/index.html` at startup rather than by anyone remembering to update it, `data:` and `blob:` images and `data:` fonts because Vite inlines small assets and fonts and the picture and screenshot dialogs preview object URLs, the serving host's `wss://` named beside `'self'` for browsers predating CSP 3, no frames, objects, foreign bases or foreign form targets — `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`, a `Permissions-Policy` declining the device and payment APIs the game has no use for, `Cross-Origin-Opener-Policy: same-origin`, and `Cross-Origin-Resource-Policy: same-origin` (`cross-origin` only when `ALLOWED_ORIGINS` names a frontend that has to load this server's images). The policy MUST NOT differ by environment: one that only production sent would be one the E2E suite never ran the built page under, and a stylesheet it blocks would be found on the day of the deploy. The Socket.IO mount and static files MUST be inside it (#467). [`security_headers.py`](../backend/app/security_headers.py) |
| **R-PLAT-22** | The process answering player traffic MUST NOT connect as a role that can alter the schema (#896). Three roles: `sketchy_owner` owns every table and is used only by the migration command (`MIGRATION_DATABASE_URL`); `sketchy_app` — the web process and operator commands — reads and writes rows and nothing else, with only `INSERT` and `SELECT` on the two ledgers `audit_events` and `score_events`, so neither an injected statement nor a wrong `WHERE` can remove a table, disable the ledger's append-only trigger or rewrite what moderation and scoring disputes rest on; `sketchy_monitor` reads statistics and no table. The migration command MUST grant the application role its privileges in the transaction that creates the tables, and production MUST refuse to start when the web connection is a superuser, owns the schema's tables or may create objects in it, and MUST refuse a migration without its own URL. The suite MUST run as the application role in CI, so a missing grant fails there. [`db/roles.py`](../backend/app/db/roles.py), [`ops/postgres/init.sql`](../ops/postgres/init.sql), `tests/test_database_roles.py` |
| **R-PLAT-21** | A startup that fails MUST report **its own** failure. The lifespan's cleanup runs whether startup finished or not, so it MUST stop only what it actually started: every background-loop handle it touches has to exist before the first step that can raise, and the finished-game drain MUST NOT run against a database that never opened. Otherwise the refusals R-PLAT-08, R-PLAT-11 and R-PLAT-19 exist to make legible arrive behind a second traceback from the shutdown path — on a short terminal, the only one the operator sees. [`main.py`](../backend/app/main.py), [`tests/test_lifespan_failure.py`](../backend/tests/test_lifespan_failure.py) |

### Planned shutdown

| # | Requirement |
| --- | --- |
| **R-SHUT-01** | `GET /api/ready` MUST return 503 **before** any drain work begins; `/api/health` remains a liveness check that reports readiness state. The shutdown state MUST be tested **first**, before the R-PLAT-12 dependency checks, so a draining process answers from the drain rather than being delayed or contradicted by a dependency. |
| **R-SHUT-02** | At drain start the server MUST send every connected client the versioned `server_shutdown` notice, and MUST refuse new room creation, new game starts, and restart votes — while leaving existing rooms connected so active games can finish. |
| **R-SHUT-03** | The drain window MUST be configurable via `SHUTDOWN_DRAIN_SECONDS` (0–300, default 30). A second termination signal MUST abandon the remaining window immediately — **whichever supported signal it is**, since a deployment stop sends `SIGTERM` twice rather than switching to `SIGINT`. The window a drain runs on MUST be fixed when the drain starts and reported from that fixed value, so a change to the configured default cannot make the notice and the deadline disagree. |
| **R-SHUT-04** | A game that outlives the deadline MUST NOT be recorded as completed history. Exactly one privacy-safe `planned_shutdown_abandonments` row MUST be written instead, retained 90 days. |
| **R-SHUT-05** | That diagnostic MUST NOT contain room codes, room or player names, prompts, chat, or canvas contents. |
| **R-SHUT-07** | An administrator MUST be able to start a planned shutdown from the operations surface, with a bounded window for this shutdown that does not change the configured default. It MUST ask the process to terminate rather than draining inside the request — a drain is one-way, and running it in a live process leaves the real shutdown nothing left to spend. A deployment whose runner cannot signal itself MUST say so rather than appear to succeed. The right to stop the process MUST be claimed once and refused thereafter — `draining` is false for the whole gap between asking and the drain starting, so without a claim a second request inside it is a second audited shutdown able to move the window the first was recorded with. A request that does not go through MUST leave the drain window and the claim exactly as it found them. Nothing in the API brings a server back. |
| **R-SHUT-06** | Live rooms, canvases, timers, scores, and games MUST NOT be serialized or restored. A crash still loses process-owned state; this is a stated property, not a defect. |

## 2. Gameplay

### Rooms and lobby

| # | Requirement |
| --- | --- |
| **R-ROOM-01** | The lobby MUST show a live list of public rooms, pushed rather than polled (R-PRESENCE-05), and MUST allow joining a private room by code. It MUST also show who is online (R-PRESENCE-01). |
| **R-ROOM-02** | Room codes MUST be six-character random invite **capabilities**, reserved in the database before being shown to a player. They MUST NOT be derived from an entity ID. |
| **R-ROOM-03** | When an ephemeral room empties, its code MUST be retired for 30 days, so a stale invite says the room ended instead of silently joining an unrelated group. Startup MUST retire reservations orphaned by a crash. |
| **R-ROOM-03a** | Codes permanently claimed by the removed persistent-room feature MUST stay claimed and MUST report a stale invite as ended. Releasing them would hand exactly those codes back to the allocator. |
| **R-ROOM-04** | Room settings MUST be settable at creation and editable by the host while waiting: name, visibility, max players (2–16), rounds (1–10), drawing time (a fixed preset list), scoring mode, hint mode, spectator prompt visibility, masked-prompt hiding, allowed tools, color mode, prompt lists, and custom prompts. |
| **R-ROOM-05** | A game MUST require at least 2 players before the host can start it. |
| **R-ROOM-06** | The host role is a **gameplay** role only. It MUST NOT confer any service-wide privilege. Conversely an administrator MUST NOT become host merely by holding the role. |
| **R-ROOM-07** | **Room** payloads MUST NOT carry account IDs. Anything that needs an account (reports, blocks, profile links) resolves the seat server-side. The lobby presence list is not a room payload: it MUST carry the account id, because there is no seat to resolve for a player idling in the lobby and a friend request needs a stable target — and it MUST NOT carry a room id, code, name, or any state beyond *in the lobby* / *in a game*, so that presence never becomes a directory of who is playing where or discloses that a private room exists. |
| **R-ROOM-13** | Room state MUST carry a player's kick and AFK vote lists only where votes exist. Every seat receives every other seat's entry on every broadcast, so an empty list per player is the payload paying a quadratic price for the state almost every player is in almost always. |
| **R-ROOM-08** | A socket MUST hold at most one live seat. Creating or joining a room MUST first release any seat that connection already holds, by the same path an explicit leave takes: room state re-emitted, timers cancelled, empty-room teardown and code retirement run. Seats MUST be matched by socket, never by account — two tabs of one account may sit in two different rooms. |
| **R-ROOM-09** | Opening a room MUST require a provisioned session. Joining, playing, and receiving a factual history seat MUST NOT — a visitor whose browser keeps no cookie can still play (R-HIST-10); they cannot host. |
| **R-ROOM-10** | Room creation MUST be bounded on four axes: live rooms per account, room creations per account per hour, live rooms per process, and quick-prompt characters retained across every live room. Each MUST be configurable, and each refusal MUST say which ceiling was reached in terms a player can act on. |
| **R-ROOM-14** | Database work on the way into a room MUST be bounded by a timeout and refuse the entry cleanly when it expires. Seat transitions hold the socket's seating gate and its disconnect queues at the same gate, so an entry that never returns is a seat that never reconciles — the leak R-ROOM-08 closed, reopened by a stall. The whole entry MUST also answer inside the client's acknowledgement wait or make nothing (#879): one deadline from arrival, below that wait, shared by every call and checked at the instant the room or seat is made - a room the player was told had failed must not exist. A repeated creation (the same `requestId` from the same account within a minute, its seat still there) MUST be answered with the room already made, not a second one, and a success the client learns of too late MUST be given back by room, never by leaving whatever room the socket is in now. |
| **R-ROOM-11** | A ceiling MUST be re-checked at the instant the room is created, not only when the command arrives: everything in between awaits, and a refusal at that point MUST release the room code it had already claimed. |

### Lobby presence

| # | Requirement |
| --- | --- |
| **R-PRESENCE-01** | The lobby MUST show every connected account, keyed by **account** rather than by socket, so several tabs of one player are one entry. A connection with no account (R-ACCT-02) MUST NOT appear, and that MUST follow from the registry's shape rather than from a filter that a later change could drop. There is **no opt-out**: this is a deliberate product decision, not an omission. |
| **R-PRESENCE-02** | Presence MUST be released the moment a socket closes, on **every** way out — including a handshake that fails after the account was registered, which never reaches the disconnect handler. It MUST NOT be held for the R-CONN-01 reconnect grace: that grace protects a *seat*, and a socket that cannot receive is not online. |
| **R-PRESENCE-03** | Presence MUST say only whether a player is in the lobby or in a game. It MUST NOT name the room, in any form, for a public or a private one alike. |
| **R-PRESENCE-04** | The list MUST be bounded and MUST report the true total alongside the bounded list, so a cap is never mistaken for a quiet server. The cap and the broadcast interval MUST both be configurable (R-ROOM-10's rule). |
| **R-PRESENCE-05** | Presence and the public room list MUST be delivered over one channel a client opts into, never a poll (#462). Each feed MUST carry its own sequence number, one acknowledgement MUST hand over both baselines, and a client MUST be able to detect a missed message and ask for a fresh snapshot, so its store is self-correcting rather than authoritative (#493). Lobby chat rides the same channel and the same acknowledgement but is exempt from the resync rule, for the reason R-LCHAT-01 gives. The baseline an arrival is handed MUST be the last completed broadcast or newer, read after the handler's lookups with nothing yielding before the answer — and it MAY be exactly the last completed broadcast, shared by every arrival until the next tick (#885), so that a herd re-asking after a restart costs one build rather than one each. A delta already on its way when the answer was built reaches the socket first, so the client MUST hold, bounded, a delta that beats the acknowledgement and replay it if newer, rather than discard it — a discarded final delta on a quiet server was a list wrong for the life of the connection (#600). The baseline MUST answer to a budget of its own (`lobby_baseline`, R-RATE-09): it is the lobby's largest message, and under the ordinary action budget one socket could pull well over a hundred kilobytes a second of it. Chat already held MUST NOT be sent again: a client holding lines from the same process and account names the last one, and is sent only newer lines. |
| **R-PRESENCE-06** | An account MUST learn which of its **friends** are online, and whether each is in a game, whatever the cap of R-PRESENCE-04 left out and without joining the lobby channel. The public list is cut at a hundred and ordered the same way for everyone, so a friend whose name sorted past the cut was never shown online and could not be invited (#878); and a waiting room had to take every row and every lobby chat line to read the few rows its invite list needed (#873). So it is answered per account, on request, and says exactly what R-PRESENCE-03 lets the public list say: in the lobby or in a game, never which room. It MAY be **polled**, and that is not the poll R-PRESENCE-05 forbids: that rule is about the public feed every lobby watches, where a poll multiplies a large answer by every watcher. This one is a few rows for one account, asked only while a surface showing friends is on screen, and a stale row costs one refused invitation, since `invite_friend` is checked when it is sent. A push stream was built for it first and cost more in ordering rules than its freshness was worth. [`services/friend_presence.py`](../backend/app/services/friend_presence.py), [`hooks/useFriendPresence.ts`](../frontend/src/hooks/useFriendPresence.ts) |

### Lobby chat

| # | Requirement |
| --- | --- |
| **R-LCHAT-01** | A lobby line MUST be delivered over the lobby channel the moment it is accepted, never from the broadcast tick, and MUST NOT be a revisioned feed: a line is an event with nothing to rebuild it from, and a gap in its numbering is *expected*, because a line is deliberately not delivered to somebody who blocked its author. A client MUST NOT resync over such a gap. The per-process `seq` exists only so the backlog and the lines that beat the acknowledgement can be put into one order without a duplicate. [`handlers/lobby.py`](../backend/app/handlers/lobby.py), [`lib/lobbyChat.ts`](../frontend/src/lib/lobbyChat.ts) |
| **R-LCHAT-02** | Anyone with an account MAY speak, a guest included — the same boundary as R-PRESENCE-01 — and only from a socket that is watching the lobby. A socket with no account MUST be able to read and MUST be refused a line, told to choose a name. Every refusal MUST come before the line is numbered or kept, so a refused line never appears in anybody's backlog. |
| **R-LCHAT-03** | Blocks MUST be honoured on both paths, by R-BLOCK-02's rule: a line by a muted author is delivered to everyone but the account that muted them, the sender included, and the backlog handed to an arrival omits the authors they muted. A socket with no account has no block list and MUST always receive. A lookup that cannot be answered MUST deliver unfiltered (R-BLOCK-06). |
| **R-LCHAT-04** | An arrival MUST be handed the recent lines in the same acknowledgement as the other baselines, oldest first and bounded (50), from memory. A restart MUST re-seed that memory from the most recent retained lines before the first socket is served — minus anything expired and anything a currently suspended account said — so a deploy does not empty the lobby; the read MUST be bounded and its failure MUST leave the process starting with an empty backlog rather than not starting. This is a buffer, not a transcript: nothing reads further back than the fifty, and N-05 stands. A client MUST keep what it holds across a dropped socket — those lines were said — and MUST replace it with the backlog of a new connection. |
| **R-LCHAT-05** | A lobby line MUST be retained under R-PRIV-07's 30 days with audience `lobby`, no room scope, no seat, and **no recipient list**: it was said to every lobby that was open, and recording every watcher per line would be a directory of who was around. It MUST be citable as report evidence through `POST /api/reports` on its own terms — the audience check does not apply to a public line, the author must still be the reported account, and a report MUST NOT mix lobby and room lines — and MUST NOT be selected automatically by an in-room `report_player`, which is scoped to that room. An account's deletion MUST take its lines out of the backlog as well as the database. |
| **R-LCHAT-06** | Lobby lines MUST answer to a budget of their own (`lobby_chat`), settable at runtime like every other (R-RATE-09), because a lobby line reaches every open lobby rather than one room's seats and tightening it must never tighten guessing. |
| **R-LCHAT-07** | Every line MUST carry the server's instant, the same one written to its retained row, and the lobby MUST show an age beside each line — fresh lines by how long ago, older ones by when or which day — so a line handed over in a backlog is never mistaken for one said just now. The payload carries an account id for R-ROOM-07's lobby reason and MUST NOT name a room. |
| **R-LCHAT-08** | A line said by another account MUST be reportable from the lobby, citing that line: over `POST /api/reports`, naming the `userId` the line carries and its `retainedMessageId`, never over `report_player`, which addresses a seat the lobby does not have. The control is the author's name on the line. A line delivered without a retained id MUST offer no report action and the lobby MUST NOT explain why — an action never offered owes no explanation, and "retention withheld this" is not something a player can act on. A player's own lines and every line seen by a guest offer none either, for R-MOD-06's reason and to match the room. The dialog offers only the reasons a line of words can be true of (harassment, spam, inappropriate name), shows the line it cites, and MAY be sent with no further detail, since the line is the complaint. ### Friends

| # | Requirement |
| --- | --- |
| **R-FRIEND-01** | A friendship MUST be mutual, and MUST be reached by a request and an answer. A request sent to somebody whose own request is already waiting MUST resolve to one accepted friendship rather than two pending ones — asking back is how you say yes. |
| **R-FRIEND-02** | A friendship MUST be stored as **one row per pair, in a canonical order**, enforced by the database. Two directional rows can disagree and nothing could forbid it. The ordering MUST also make a self-friendship impossible, and the account that asked MUST be one of the pair. |
| **R-FRIEND-03** | Both sides MUST be registered accounts. A guest identity is a browser rather than a person and is purged after a month of not playing, so a friendship with one would outlive the account and vanish unexplained. The caller MUST be told why; the target MUST NOT be. Note the deliberate asymmetry with R-BLOCK-01: a block is a protection and every account has one, a friendship is a convenience. |
| **R-FRIEND-04** | A request MUST be answered identically whether it landed, hit a block, hit an earlier refusal, or named an id that was never an account. Anything else makes the endpoint a way to learn who has blocked you, or which ids are real. The only refusal that may name its reason is a ceiling the caller themselves reached. |
| **R-FRIEND-05** | A decline MUST be durable, so it cannot simply be re-sent into. The *answer to the request* MUST be indistinguishable from success (R-FRIEND-04), and no event, message or listing may name a decline or the account that made one. What is **not** promised is that a sent request stays on the sender's list forever: a sender who may withdraw a request has to be able to see it, so a request that stops being pending stops being shown, and an attentive sender can infer what happened. Concealing that would mean showing them a row that is no longer true, and the list is what they act on. The person who declined MUST still be able to ask in their own right later: saying no is not a commitment. Cancelling a request or ending a friendship MUST delete the row instead — neither is a refusal, and neither may suppress a future request. |
| **R-FRIEND-06** | A player seated in a room MAY invite a friend into it. The invitation MUST carry no room code, name, or id: it is a token the server resolves against the sender's live seat, so it cannot be forwarded, stops working when the sender leaves, and never tells anybody the code of a room they were not seated in. It MUST be single use and MUST expire. |
| **R-FRIEND-07** | A friend MAY take a seat in a room they cannot name. Uninvited, this MUST resolve only rooms whose **host** is an accepted friend of the caller — otherwise a private room gains a player because one of its occupants knows them, and the host never agreed. With an invitation, the sender's own seat is the consent, and the invitation names the room its **sending socket** was in. Resolution MUST NOT depend on iteration order: an account may hold seats in two rooms at once (R-ROOM-08), so a request that could mean either MUST be refused rather than answered with whichever was found first. |
| **R-FRIEND-08** | Entry by either path MUST run the ordinary seating lifecycle — the seating gate, R-ROOM-08's release of any seat the socket held, R-RATE-06's limits with their refunds, capacity, and the suspension checks on both sides of seating. It MUST NOT re-derive them. |
| **R-FRIEND-09** | Friendships MUST be bounded per account and MUST be rate limited, and the bounds MUST hold under concurrency: a request and an accept lock both accounts' rows, ascending, before counting, so two writes at one below a ceiling cannot both pass (#898). Each refusal MUST name what was reached in terms the caller can act on — except one that would disclose a third party's state, which MUST stay generic. Every rule a friendship obeys - its ceilings, its rate limit, its silences, and telling the other account that their lists moved - MUST be enforced where the friendship is written rather than beside one of its callers, so that a second way in cannot be given a weaker rule than the first. Merging a guest into an account MUST carry its friendships across under R-BLOCK-04's rules, keeping the stronger status where a pair already exists. |
| **R-FRIEND-10** | Friends MUST be reachable from every screen, and reaching them MUST NOT cost a seat. A request can arrive while its recipient is drawing, and a surface that has to be navigated to would make answering one a choice between the answer and the game. So it is an overlay on a route — the mechanism R-SET-06 already defines, generalised rather than written twice — drawn over the page it was opened from, linkable, and closing back to that page. It MUST show accepted friendships, requests received and requests sent, whether or not the other account is online: the lobby's presence list answers *who is around*, which is a different question, and neither an offline friend nor a request waiting to be withdrawn appears in it. A decline and an unfriend MUST be confirmed before they happen — a decline cannot be undone by the person who made it (R-FRIEND-05), and an unfriend revokes a way into a game — while cancelling a sent request MUST NOT be, because it leaves nothing behind. Requests MUST be answered **here and nowhere else**, with one exception: the arrival notice of R-FRIEND-12 may carry *Accept*, because that is the answer almost always wanted and it is not the one that is kept. A decline MUST NOT be reachable from anything that disappears on its own. |
| **R-FRIEND-11** | Reaching one specific person MUST NOT require them to be present. A friendship offered only by a lobby row or a shared seat can only ever be offered to whoever is there at that moment, and the person somebody wants is usually the one they finished a game with yesterday. So a profile MUST offer it, and a lobby presence row MUST link to the profile — presence already carries the account id for exactly this reason (R-ROOM-07). The presence list itself MUST carry **no request state**: no report of a request in either direction, in words or by an offer's absence. A row there comes and goes as people open and close tabs, which makes it the wrong home for one — a request it reported could be answered only while its sender happened to still be standing there. A row MAY *offer* the ask, from a menu that also opens the profile, as the room's seat menu already does: an action taken once and finished is not state to be read, and a row that already knows whether somebody is a friend — it offers **Join** on the strength of it — can offer to become one. What it MUST NOT do is consult, or reveal, an outstanding request: the offer stands whether or not one exists, and pressing it is what the server resolves, since a duplicate changes nothing and asking somebody who has asked you accepts them. The earlier rule forbade the offer as well; that went too far, and cost the lobby the one thing people actually wanted from a row. What may stay is entry into a friend's game (R-FRIEND-07), which is about the game rather than about the friendship. The service MAY also suggest accounts the caller **finished a game with** recently; such a list MUST be derived only from games the caller themselves sat in, so it can never name a stranger (N-06), and it MUST NOT be filtered by friendship or block on the server, because an absence from it would disclose what R-FRIEND-04 refuses to. A profile MUST also **state** an existing friendship rather than falling silent: a page with no control on it reads the same whether the two are friends, whether the viewer is signed out, or whether it has not finished loading, and it is the natural place to ask. Ending a friendship MUST NOT be offered from a profile: it is confirmed on the friends surface (R-FRIEND-10), and a Remove button beside somebody's statistics is one mis-click from revoking a way into a game. |
| **R-FRIEND-12** | A friend request arriving, and one this account sent being accepted, MUST both be told — from any screen, a live game included. Both were silent, and a notification a player only sees by happening to be on the right page is not one. What happened MUST be derived by comparing the friend lists across the refetch that `friends_changed` triggers, rather than by putting it in the event: the event stays one contentless shape covering both directions, with the listing endpoint as the truth. A request that stopped being pending MUST NOT be announced — the sender's list no longer showing it is what R-FRIEND-05 permits, and naming the refusal is not — and neither MUST a friendship the reader made themselves. The notice for a request arriving MUST offer **Accept**, and MUST last long enough to be read and reached mid-turn: the alternative is opening a menu, then a surface, then finding a row, for the one answer that is almost always intended. It MUST NOT offer Decline — a refusal is kept (R-FRIEND-05), and a permanent answer does not belong on a control that removes itself on a timer. Several arriving at once MUST offer the surface instead, because one button cannot mean four people. The number of requests waiting MUST be shown on the control that opens the friends surface, and MUST be reachable to a screen reader as part of that control rather than as a loose number beside it. |
| **R-FRIEND-13** | A friendship MUST be legible at a glance wherever a player is drawn, as a **mark on the avatar disc** rather than as words beside the name. The disc already carries the viewer's own ring and the host's crown for the same reason — a roster has no width to spend on a label, and one shape read in one place looks the same on every surface. It is **per-viewer**, like the ring: it says something about the relationship between whoever is reading and whoever is drawn, and is not a fact about the game. It MUST NOT rely on colour alone, because a player's own colour, the ring, the crown and the guest dot already spend the palette around that disc and a colour-only mark would be one more thing to tell apart; and being decorative, it MUST be spelled out in text by whatever draws the name, so it reaches a screen reader in the right order. It MUST be drawn wherever a friend appears **among people who are not necessarily friends**, and on every such surface rather than only the one that happens to fetch it: a narrow layout swaps the room's roster for a different component entirely, and a mark that belongs to one panel disappears with it. Two kinds of surface are deliberately outside that. A list that is *entirely* friends — the friends surface's own accepted section, the invite list a seated player picks from — is already saying so in its heading, and a mark on every row there is decoration rather than information. And the roster of a room the viewer is **not in** MUST NOT be marked at all: `to_public_roster` carries no seat id and no account id on purpose, so marking would mean the server confirming which stranger-nicknamed seat is a friend — and it would say *which room* a friend is in, which presence deliberately refuses to (R-ROOM-07). **Inside a room** it MUST be resolved server-side and named by **seat**: the room's payloads keep carrying no account id (R-ROOM-07), and the answer is addressed to the one socket that asked, because every reader's is different. That is not the per-player game state R-BLOCK-03 forbids — that rule is about a *block* hiding gameplay facts, and this hides nothing and decides nothing. A caller who cannot have friends MUST be answered like one who simply has none here. |

| **R-GAME-01** | A game MUST proceed as: waiting → *choosing* (15 s) → *drawing* (room-configured, default 90 s) → *turn results* (5 s) → next turn → *game over*. ### Scoring

| # | Requirement |
| --- | --- |
| **R-SCORE-01** | Everyone MUST start a game on zero points, in every scoring mode. |
| **R-SCORE-02** | Three modes MUST be offered: **Default**, **Pressure**, **No scoring**. |
| **R-SCORE-03** | **Default**: a correct guess scores `round(100 + 200 × remaining / drawing_seconds)` — between 100 and 300 points, falling linearly. |
| **R-SCORE-04** | **Pressure**: starts at 300 and decays exponentially (~2 %/s at the 90-second reference), the rate **doubling for everyone still guessing** once the first player answers. Floored at 50 gross. The per-second rate MUST be derived from the room's own drawing time so the curve has the same shape in a 15-second room and a 300-second one. Because the penalty scales with the *gap* after the first correct guess rather than applying as a step, a near-simultaneous second guess loses only a handful of points. |
| **R-SCORE-05** | **No scoring** games MUST still detect correct guesses and end turns normally, MUST leave everyone on zero, and MUST NOT show standings. They MUST record the same factual per-seat outcomes with zero awarded points, and MUST NOT invent hypothetical awards. |
| **R-SCORE-06** | **Hints are bought on credit.** Nothing is charged when a hint is bought; the turn's total hint spend is subtracted from that turn's guess award, floored at zero: `turn_score = max(0, guess_points − hint_spend)`. A turn can be wiped out, but a running total MUST NEVER go down, and hints MUST cost nothing to a player who never guesses the prompt. |
| **R-SCORE-07** | Hint spend MUST be capped at 300 per turn — the most a single guess can ever be worth. In Pressure mode the 50-point floor guarantees the **gross** award only; hint spend settles after it. |
| **R-SCORE-08** | The drawer MUST receive the sum of the **net** points earned by all correct guessers in that turn. This is the anti-sandbagging property: a drawer cannot game an easy prompt by stalling, because their bonus scales with how fast guessers actually answered. |
| **R-SCORE-09** | Standings MUST use standard competition ranking (1, 2, 2, 4). The live standings and the recorded ones MUST share one implementation, so a final screen saying two players tied for first cannot be written down as a first and a second. [`game.py:53`](../backend/app/game.py) |
| **R-SCORE-10** | Changing any outcome-producing constant or algorithm MUST bump `SCORING_RULES_VERSION`, and every completed game MUST freeze the full rule snapshot used for its scores. |

| **R-HINT-01** | Four modes MUST be supported: `none`, `checkpoints` (letters revealed to everyone at fixed points), `purchase` (a guesser buys a letter **slot**, visible only to them), `wheel` (a guesser buys a specific **letter**, revealing every occurrence, visible only to them). |

### Drawing

| # | Requirement |

| **R-DRAW-01** | The canvas MUST be synchronized in real time across every client in the room, including late joiners. That interval is the **drawer's** transport's — 80 ms on a WebSocket, 240 ms on long-polling, where every flush is an HTTP POST carrying more header than frame (#887) — so a viewer of a drawer on polling sees ink up to 240 ms behind the hand rather than 80. ### Reactions to drawings

A **Reaction** is one emoji a registered player leaves on a turn's drawing (#520). It
follows the drawing to every surface the drawing is shown on — the live canvas, turn
results, the **Recap**, and game history — and is a fact *about the drawing*, which is
what decides where it is stored and when it goes.

| # | Requirement |
| --- | --- |
| **R-REACT-01** | Only an account with lifecycle `registered` MUST be able to react — a seat in the room, or since #524 any registered account that can see the drawing in the **Gallery** or on a pinned shelf. Guests and cookieless seats see reactions but cannot give them. **Not** email verification: registering does not require an address, so a verified-email gate would lock out ordinary registered players, and the R-LIST-12 trust gate is refused for the same reason — the cost of a pile-on is accounts, each rate-limited (R-REACT-12), and that is accepted. |
| **R-REACT-02** | Spectators MUST NOT react. The drawer MUST NOT react to their own drawing — checked by seat **and** by account, because a drawer who left and rejoined holds a new seat. A seat ineligible to guess (AFK, disconnected at freeze) MAY react: they can see the drawing. |
| **R-REACT-03** | One reaction per registered account per drawing, chosen from the fixed positive **Reaction set**, changeable and removable at any time. Uniqueness MUST be a database constraint on `(turn, account)` — the row carries the reactor's **canonical** account (`user_id`), and the participant seat beside it when the reactor sat in that game, null when they did not. The seat constraint `(turn, participant seat)` stays as a second rule for the rows that carry one. Alias resolution happens **before** the write, on the caller, so one person merged from two identities still holds one row. |
| **R-REACT-04** | Reactions MUST be accepted from the moment the drawing is visible: during the Drawing phase and at turn results for the **current** turn only, in the Recap, and from game history at any later time. An earlier turn of a live game is no longer on anyone's screen and MUST be refused. |
| **R-REACT-05** | A live reaction MUST be broadcast to the whole room, the drawer included, and room payloads MUST carry the reactor's seat token and presentation only — never an account id (R-ROOM-07). State payloads (`turn_started`, `sync_game`, `turn_ended`, recap metadata) MUST carry the reaction **list**, not only a tally, so a reconnecting client recovers its own pick. A reaction given from **outside** the room (R-GAL-06) has no seat and is **never attributed**: history, pin and gallery payloads carry the seat rows as a list and every row as a per-code **count** (`reactionCounts`), plus the caller's own pick (`myReaction`), so a tally is complete while no outsider's name ever rides a drawing. |
| **R-REACT-06** | Reactions given while a game is live MUST be kept on the `Room` and folded into the all-or-nothing finished-game write (R-HIST-03), for a completed **and** an abandoned game (R-HIST-05). A game lost with the process loses them (R-SHUT-06). |
| **R-REACT-07** | A reaction given from the Recap or from history is a write to a finished game and MUST go through one repository path shared by the socket and the REST route. It MUST refuse while the history write is still pending, and when the game was never recorded. It MUST NOT touch the score ledger (R-HIST-11): reactions are not scored. |
| **R-REACT-08** | The REST write for a participant MUST sit beside the drawing route and **every refusal MUST be a 404** (R-HIST-16) — stranger, guest, drawer, erased drawing, unknown code and unknown game alike. | **R-REACT-09** | Emoji MUST be stored as stable codes with the set version, never as glyphs. A code, once shipped, MUST NEVER be removed or reused (the stored-drawing rule, R-HIST-18): retiring one stops it being offered and nothing else, so old history keeps rendering. Adding one is additive and bumps the set version. |
| **R-REACT-10** | A reaction is keyed by the reactor's account, and a deleted account is a tombstoned row, never a removed one (R-PRIV-08), so a deleted reactor's reaction **still counts**; where it carries a seat, that seat reads as **Deleted player**. An **Erased** drawing MUST take its reactions with it and accept no new ones; the turn and its scores remain. |

| **R-REACT-12** | Reactions MUST answer to the existing per-caller `action` budget (R-RATE-08) and MUST NOT get a budget of their own. |

**Pinned drawings** are the up-to-six drawings an account chose to show at the top of
its profile (#440). A pin is the pinner's act, not a fact about the drawing: it is kept
on the account, not the seat, and it discloses nothing the game's public listing did not.

| # | Requirement |
| --- | --- |
| **R-PIN-01** | Only an account with lifecycle `registered` MUST be able to pin, and only a turn from a game the pinner **sat in** — their own drawing or another player's. | **R-PIN-02** | A profile MUST hold at most **six** pins (`PROFILE_PIN_SLOTS`), in an order the owner controls, and the cap and the order MUST be schema constraints (`position` in `0..5`, unique per account) rather than only a check in the write path. Spectators, guests and private rooms see no control; a guest is not told a second time how to get an account, since the reaction control beside the same drawing already says it. Pressed from the game-over screen inside the window before the history write lands (R-HIST-26), the route's 404 MUST be said as *still being saved, try again*, the recap reaction's answer, because on that screen it means nothing else. ### Gallery

The **Gallery** is every kept drawing from a public game, shown to people who were not in
the game that produced it (#524). It is the deliberate exception to R-HIST-16, and it is
built as a surface of its own — a predicate, a route and a query — rather than as a
relaxation of the participants-only rule, so widening one can never loosen the other.

| # | Requirement |
| --- | --- |
| **R-GAL-01** | A drawing MUST be in the Gallery exactly when its game is **public** (R-HIST-25), its stored drawing is `ready`, and no moderator has hidden it (R-GAL-09). Nothing else admits or excludes it — not a reaction, not a pin, not the drawer's wish. Playing in a public room, which the lobby listed with its players' names, is the consent (the R-PIN-03 rule), and the way out of an entry is a report and erasure (R-PIN-01's rule for a pin). An opt-in was refused because it makes the Gallery a shelf of self-selected work, and an opt-out because it hands one account a veto over every other player's history of that game. |
| **R-GAL-02** | The Gallery MUST be readable by **any session**, a guest's included, and by **no one without one**: a visitor with no session gets no page, no shelf and no bytes — the page's route refuses as `account_required` so the client can say why, the bytes are a 404 like every other refusal, and the client renders the page and the shelf as absent, not empty (R-PIN-06). Signed-in is the line because it is what separates a player from a scraper, and the Gallery is the one surface on which every public drawing is one query away. |
| **R-GAL-03** | A Gallery entry MUST publish what a pin publishes and nothing more (R-PIN-07), on the feed and on the drawing's own page (`/gallery/{turn_id}`, which exists because a drawing worth a reaction is worth a link, and which replays the stored actions stroke by stroke — the one thing a gallery of actions can do that a gallery of pictures cannot, R-HIST-15): the drawing, the prompt, the round and turn, the drawer's **frozen** snapshot (#387), the game's finish time, the reaction counts and the viewer's own pick. It MUST carry **no game id**, no room name, no other player and no reactor's name. Each of those is a separate release of something participants-only, and none of them is needed to look at a drawing. Reading a page MUST cost work bounded by the page, never by how many reactions its drawings hold: counts come grouped by code and only the seat rows are listed, because anyone signed in may react and one drawing's rows are bounded by nothing a page should have to instantiate. |
| **R-GAL-04** | The Gallery MUST offer three orders — **Hot**, **New** and **Top** — and Top MUST be windowed **all time / month / week**. The metric is the number of reactions. New is the latest game finish first. Top is most reactions first. Hot is `log10(max(reactions, 1)) + finished_at / 45 000 s`, so a decade of reactions buys twelve and a half hours, read over a bounded horizon of fourteen days — with at most sixteen seats a room's own verdict cannot buy more than a day, so nothing older can be hot. Every order MUST break ties deterministically: earlier game finish first, then turn id, so two reads agree and a page never shows an entry twice or skips one for a tie. Pages are an opaque cursor of at most 24 rows, and paging **stops 480 rows deep** with an empty page — the community catalogue's rule, for the same reason: nobody reads that far, so a deeper page is a scrape and a different order is the better answer. |
| **R-GAL-05** | Top over the whole history cannot count rows on read, so each drawing MUST carry its `reaction_count` and its Hot `hot_score` on its `turn_drawings` row, set from the rows **inside the transaction** of every reaction write, under the row's lock so two reactions landing together cannot each count only their own, and of the finished-game write; both MUST be **disposable projections** (R-HIST-21's rule): the rows are the facts, an operator command rebuilds them from the rows, and a rebuild reproduces exactly what the writes left. The score lives on the row rather than in the query because one row's score never changes except when its count does — the decay is the newer rows' larger second term — and because a logarithm in SQL is not something both engines spell alike. A count that is a counter — incremented and trusted — is what N-03 refuses, and it would drift on the first retried write. |
| **R-GAL-06** | The Gallery's bytes route MUST be its own route and its own query, authorised by the gallery predicate of R-GAL-01 alone — the **third door** beside the participant route (R-HIST-16) and the pin route (R-PIN-06), never a disjunction in either — with the same validator, `304` and `private, no-cache` handling as those two (R-HIST-24), so a drawing that leaves the Gallery stops being served at once, including to a remembered validator. A place for it in the **lobby** was built and then withdrawn (2026-09-16): the lobby on a wide screen is a fixed shell in which the rooms take what the people row leaves, and a third panel of six replayed frames squeezed both without earning its keep; a lobby placement stays open, and the options drawn for it live on the design canvas. A hidden drawing stays hidden whatever the switch says. |
| **R-GAL-11** | The Gallery MUST be a **static surface in every language** (R-I18N-04): its orders, windows, empty states and every refusal come from the catalogue, and the drawer's name and the prompt are the frozen facts they are everywhere else. An offer **ending** MUST reach a connected account as surely as one arriving does, and by the same route: the entry it asks for is shown only to an account with an offer, so a browser that missed either would show the wrong thing until a reload — nothing to enrol from with an offer standing, or a way into an enrolment that would grant nothing after one was withdrawn. A **passkey** satisfies this on its own and needs no such column: registering one demands the password (R-AUTH-23), so every row in `user_passkeys` is already proof. It vouches for **itself and nothing else**: registering a passkey MUST NOT mark an authenticator app as proved, or a factor planted with a stolen cookie would become trusted the moment its victim added a passkey — the same attack, through a side door. A promotion MUST therefore look for either — an account that was staff before still holds the passkey it signed in with, and offering it a role it cannot take up (the browser refuses a second credential for one it already holds) is a promotion that never lands. Taking an offer up MUST revoke every **other** session for the reasons a grant does, and MUST leave the browser that did it signed in — with a session carrying the staff lifetime (R-AUTH-03) — because it proved a password and a code one request ago, which is more than the sign-in it would otherwise be sent to, and because the recovery codes in that same response are shown exactly once and would go off the screen with it. **Replacing** a factor MUST still prove it, because that destroys a credential the way removing one does — and so MUST **adding** one to an account that already holds any credential of either kind, since a session thief who can bind an authenticator app of their own choosing can step up with its codes without ever holding the password. An authenticator app whose owner was never proved MUST NOT satisfy **step-up** (R-AUTH-21), even though it may sign in beside a password: a sign-in costs an attacker the password they have not got, where a step-up would cost only the session they already stole. Such a factor can exist on a staff account — planted while it was an ordinary player, and carried along by a promotion granted on a passkey — and confirming it (`confirm-owner`) is what makes it usable again. A player's second factor does **not** gate their sign-in — it is preparation for a role — and that is deliberate for the same missing-recovery reason: R-AUTH-14 gives a way back from a lost password and nothing gives one back from a lost authenticator, so gating an ordinary player's login on one would be a lockout with no key. A staff account MUST NOT be able to remove its own second factor; giving up the role is what removes the requirement. Because a role change ends every session, the role-change notice (R-ROLE-02) pushed at that moment MUST offer the way back in rather than an acknowledgement the browser no longer holds a credential to make; the notice stays pending and is acknowledged on the next visit. `STAFF_SECOND_FACTOR_REQUIRED=0` exists only for a deployment that has just promoted its first moderators, and leaving it off is leaving this requirement unenforced. ### Authentication rate limits

| # | Requirement |
| --- | --- |
| **R-RATE-01** | Login, registration, and lookup limits MUST be persistent, shared database buckets, so they survive restarts and apply once across every replica. A limit MUST NOT be decided by reading a bucket, deciding in the application, and writing it back: every statement MUST carry its own condition, so the database evaluates the ceiling against the row as it stands. `SELECT … FOR UPDATE` MUST NOT be relied on for this — SQLite ignores row locks and is the documented default, so a read-then-write ceiling is soft by however many attempts are in flight together. |
| **R-RATE-02** | Bucket keys MUST be HMAC-SHA-256 digests under `IP_HASH_SECRET`. **Raw IP addresses MUST NOT be stored.** |
| **R-RATE-03** | Expired buckets MUST be cleaned in bounded batches. |
| **R-RATE-04** | Rotating the secret MUST start fresh buckets without exposing or re-identifying old keys. |
| **R-RATE-08** | Every client-originated Socket.IO command MUST answer to a per-caller budget, sized by what the client actually does: drawing at the drawer's own flush rate, conversation at a message or two a second, a floor between full canvas replays, and a human's pace for everything else. The budget MUST be checked **before** parsing, authorization or mutation, so a refused command costs only the check. Windows MUST be keyed by the **kind** of traffic rather than by the command, or two commands of one kind each get the allowance their kind was given. A refusal MUST do no work: `draw` frames, which nobody awaits, MUST drop silently (a refusal the client must act on — a stale generation, a refused tool, an undecodable frame — reaches it as one coalesced `canvas_stale` notice per resync window, never as a history dump; R-DRAW-13), and every command a person pressed a control for — `undo_stroke` included, which shares drawing's budget but is awaited — MUST answer a bounded acknowledgement rather than leave them looking at a control that did nothing. Exhaustion MUST be recorded as a runtime observation **once per window** — not once per refusal, which would be the write amplification the budgets exist to stop, and not once per caller, which would make a two-second mistake and a twenty-minute flood indistinguishable. |
| **R-RATE-09** | Budgets MUST carry their default, bounds and purpose beside them, and MUST NOT be read from the environment: #446 tunes them from an admin panel without a deploy, and a value fixed at startup forecloses that. The bounds MUST refuse a limit the client cannot live with — drawing below the drawer's own flush rate is not a setting, it is a broken room. |
| **R-RATE-11** | A socket's outbound backlog MUST be bounded per connection, measured at the point every packet is queued: past a queued-age bound (10 s, re-read on a timer, since age is time rather than traffic) or a byte bound (4 MiB) the socket MUST be closed and its queue discarded whole — never drained selectively, so no draw packet is dropped mid-stream — with an abort that waits on nothing, so a stalled writer can never hold the worker, and counted by reason. Recovery MUST be the ordinary one: reconnect, rebind inside the grace, a full verified sync (R-DRAW-01). A slow socket MUST NOT delay any other recipient's fan-out (#602). [`socket_server.py`](../backend/app/socket_server.py) |
| **R-RATE-10** | An inbound Socket.IO packet MUST be judged **before any of it is retained**: a binary envelope may name only `draw`, declare exactly one attachment, carry the client's exact placeholder shape and at most the action identity; an attachment MUST NOT exceed the largest frame the codec produces (`MAX_FRAME_BYTES`); an assembly MUST expire (5 s) and MUST be dropped by text arriving inside it; a socket's packets MUST be counted before decoding against a ceiling derived from the drawing budget's tunable maximum (its maximum + 100 per second, an attachment not counted) so it stays above every legitimate cadence including a post-stall burst; a command MUST be refused for surplus arguments before its handler runs. A refused packet MUST NOT be answered — a reply per malformed packet is the amplification a flood wants — and MUST be counted by reason; a socket refused more than 20 times in a second MUST be closed. Reason: R-RATE-08's budgets run only after the library has rebuilt an event, and the library keeps every declared attachment until the count is met, so without this a connected client could hold declared-count × 1 MiB per socket on the single worker before any budget acted (#596). [`socket_server.py`](../backend/app/socket_server.py), [`handlers/context.py`](../backend/app/handlers/context.py) |
| **R-RATE-12** | Login MUST be counted against **three** keys, not one: the **account** (a keyed hash of the lowercased username — never the username, so the table is not a list of which accounts exist or which are under attack), the **address**, and the **deployment**. An address-only limit is no limit at all against a botnet, which never reuses a key; the account bucket is what makes guesses against one username add up however many hosts they arrive from. All three MUST count **failures only** — a correct password costs nothing, which is what lets the ceilings be low enough to matter without locking out a household. Consecutive failures on one account MUST additionally buy an increasing lockout (1 m, 5 m, 15 m, 1 h from the third), remembered **across** rate-limit windows in `auth_login_lockouts` and cleared by one correct password, because a fixed window forgets a slow attack between each attempt. A lockout untouched for a day MUST be removed by the hourly retention sweep (6 h SLA): failures are counted for usernames that do not exist, so without it every name anybody tried would be kept for ever — a table an unauthenticated client grows at will, and a list of what was guessed (#891). A refusal MUST say the same thing whichever key refused and whether or not the account exists (R-AUTH-09). The deployment-wide bucket MUST NOT refuse a caller who has no failures of their own: fifty addresses spending their own allowance fill it, and refusing on it alone would turn every correct password on the deployment into a 429 until the window rolled — a lever rather than a ceiling. Once full it refuses only callers whose account or address key already carries failures, which holds a spray to one attempt per key while everybody else signs in as usual. It stays disableable (`AUTH_LOGIN_GLOBAL_LIMIT=0`); N-17 records what it deliberately is not. [`auth/login_guard.py`](../backend/app/auth/login_guard.py) |
| **R-RATE-07** | Guest provisioning MUST be bounded per address **and** by a daily ceiling for the whole deployment — the bucket is a shared database row, so replicas count against one number, not one each — and stale guest rows MUST be purged on a schedule the application owns. A retention policy nothing runs is not a policy. |
| **R-RATE-06** | Seating joins MUST be rate-limited per socket, and rebinding an existing seat to a new socket MUST be rate-limited **per seat** — a per-socket key cannot see that churn, because every attempt arrives on a new socket with a fresh allowance and the one it supersedes is closed. Confirming a seat already held MUST NOT be charged: a client heartbeats through that path, and a liveness check must never be able to lock a player out of their own room. |
| **R-RATE-05** | The room-creation limit MUST use the same persistent buckets, keyed by **account**, and an attempt that opens no room MUST be given back rather than spent. A per-address key MUST NOT be introduced until a trustworthy client address exists to key on: behind a reverse proxy every socket presents the proxy, and the forwarded header is attacker-controlled. |

## 6. Connection resilience

| # | Requirement |
| --- | --- |
| **R-CONN-01** | On disconnect, a player MUST have 30 seconds to reconnect with their private stored secret and keep their score and place in the turn order. |
| **R-CONN-02** | A successful reconnect MUST replace the player's active socket, so the superseded socket can no longer issue commands. |
| **R-CONN-03** | If the drawer disconnects and does not return in time, their turn MUST be skipped and they MUST be evicted from the rotation. |
| **R-CONN-04** | If everyone disconnects, the room MUST be cleaned up — and if a game was live, an `abandoned` game record MUST be written. |
| **R-CONN-05** | An action that expects an answer MUST NEVER be handed to a socket that is not connected. It waits for the connection and is sent once, or it times out **having never been sent** — so a request reported as failed cannot arrive later on reconnect. |
| **R-CONN-06** | Actions that only make sense in the moment (a guess, a vote, leaving, toggling AFK) MUST be dropped outright rather than replayed into whatever the room has become. A retry of such an action MUST be sent only inside the scope the first attempt was made in — the same connection, room and turn — and the action MUST carry that scope so the server can ignore, before any effect, one whose scope its seat has left: a transport's `connected` flag establishes no gameplay scope (#599). |
| **R-CONN-07** | A disconnect MUST reconcile against every room the socket actually holds a seat in, rather than the single room its session names, so a seat stranded by an earlier build still becomes disconnected and is evicted on the ordinary grace. |
| **R-CONN-09** | A socket whose protocol version differs from the server's MUST be accepted, told to upgrade, and then **held to it**: every command it sends MUST be refused with `protocol_mismatch` before parsing — no room created or joined, no frame recorded, no lobby watched — and the socket MUST be closed after a short bound (5 s) if it has not gone by itself. The check MUST come after admission, so capacity (R-CONN-08) and suspension outcomes stay distinct. A refusal at the handshake would hand a stale build nothing to act on; an accepted-but-unenforced socket let one play on a contract the server no longer spoke (#476). [`handlers/context.py`](../backend/app/handlers/context.py), [`handlers/connection.py`](../backend/app/handlers/connection.py) |
| **R-CONN-10** | The client MUST reload at most once per server version, and when the same version is seen again after that reload it MUST stop reconnecting and show a visible **update required** state with a reload the player chooses, which forgets the automatic reload already spent. A stale tab MUST be either reloading or saying so — never silently refused, and never in a reload or reconnect loop (#476). [`lib/protocol.ts`](../frontend/src/lib/protocol.ts), [`lib/updateRequired.ts`](../frontend/src/lib/updateRequired.ts) |
| **R-CONN-11** | Every HTTP response MUST carry the server's `PROTOCOL_VERSION` in `X-Sketchy-Protocol`, and the client MUST compare it on every response it reads, taking the same reload-once path as the socket notice with the same marker, so a tab that is not on a socket is caught by its next request. A header that is absent or not an integer MUST be ignored, never read as a skew. The REST surface has no version of its own (N-13). [`request_timing.py`](../backend/app/request_timing.py), [`lib/api.ts`](../frontend/src/lib/api.ts) |
| **R-CONN-12** | A visible, seated client MUST reconcile its seat, phase and round with the server through `session_ping` at least every **15 s**, and MAY skip a 5 s tick only when an authoritative phase event (`turn_starting`, `turn_started`, `turn_ended`, `sync_game`, `room_state`) reached it inside the last interval and agrees with what it holds. Unrelated traffic — draw frames, chat, config notices, transport pings — MUST NOT extend that deadline, because it proves liveness and nothing about the seat (#564). A reply MUST be judged against the state held when it lands and only from the socket, room and seat it was sent on. Repeated-failure escalation is R-CONN-14's; the phase-stall check is unchanged. A tab returning to view MUST reconcile only when it has something to reconcile — hidden longer than that 15 s, or nothing authoritative while it was away — because a hidden tab keeps its socket and keeps receiving; every return used to cost a `join_room` and a `sync_game` per seat (#886). [`lib/heartbeatSchedule.ts`](../frontend/src/lib/heartbeatSchedule.ts), [`hooks/useRoomSessionReconnect.ts`](../frontend/src/hooks/useRoomSessionReconnect.ts) |
| **R-CONN-13** | A seat that resyncs mid-turn (a reload, a reconnect, or a tab returning to view) MUST get back which seats have guessed, in guessing order with the server's times, and — privately — its own correct guess and its breakdown. Both are otherwise announced once, and a tab returning to view resyncs, so without them the most common recovery path re-opened a correct guesser's input and cleared everyone's progress (#870). |
| **R-CONN-14** | Clients MUST NOT all come back at once. After a planned restart each MUST hold its first attempt a random part of the window the `server_shutdown` notice names (`reconnectSpreadMs`, set by the operator because only the server knows how many clients it has), and the REST refetches a reconnect triggers MUST be spread behind it; an ordinary drop MUST back off with jitter. A run of missed `session_ping`s MUST NOT restart a transport the server is still keeping alive: that is a slow server, every seat misses together, and a restart asks for the whole canvas at the moment it can least be afforded — so it MUST be a soft rebind, a restart only for a silent transport, each escalation backed off (#872). A room MUST wait out a deploy before marking its seat as failed. A network coming back (`online`, or a `pageshow` from the back/forward cache) MUST NOT be left waiting out a backoff measured against a network that is gone: the client reopens at once, which means closing first — a bare reconnect call opens nothing while the manager holds a pending retry — except during the restart spread above, and except while an attempt is already in flight, since that close would abort the handshake and an interface that flaps would interrupt every attempt it asked for (#886). [`lib/reconnectPolicy.ts`](../frontend/src/lib/reconnectPolicy.ts), [`lib/socket.ts`](../frontend/src/lib/socket.ts), [`hooks/useRoomSessionReconnect.ts`](../frontend/src/hooks/useRoomSessionReconnect.ts) |
| **R-CONN-08** | The process MUST bound how many sockets it holds at once, configurably. A socket past the ceiling MUST be **told and then closed**, never refused at the handshake: `ConnectionRefusedError` is reserved for suspensions, and a refusal carries no signal the client can explain to a player. The ledger MUST be keyed by socket id rather than counted, so a missed or repeated close cannot drift it, and it MUST be balanced on **every** way out of the handshake — a refusal never reaches the disconnect handler, so a socket counted in and refused out would hold its place for ever. |

## 7. Moderation and safety

### Reports

| # | Requirement |
| --- | --- |
| **R-MOD-01** | Any signed-in player, **including a guest account**, MUST be able to submit a private report. Reports use one of six bounded reasons (harassment, offensive drawing, inappropriate name, cheating, spam, inappropriate avatar) plus ≤ 2000 characters of detail and an optional ≤ 32 KiB JSON context snapshot. The detail MUST be optional on both routes: the evidence — the cited lines, the drawing — is usually the whole complaint, and a reporter mid-turn, or one reporting a lobby line from the line itself, is not made to write it out. An empty detail is stored empty and shown as *no details given*, never padded with stand-in words a moderator could read as the reporter's. |
| **R-MOD-02** | A player report from a **room** MUST name their **seat**, never their account. Wanting to complain about somebody is not a reason to learn their account ID. The lobby is the one exception, and only because there is no seat: a lobby line already carries its author's account id for R-ROOM-07's reason, and a report of it names that id over REST (R-LCHAT-08). |
| **R-MOD-03** | The **server** MUST select the evidence — the reported player's recent messages as the reporter actually received them — which makes *"is this message theirs"* and *"did you see it"* true by construction rather than checks against a client's claims. |
| **R-MOD-04** | Up to 20 unexpired messages may be pinned, and only when the reported player authored them and the reporter was in each stored audience. Expired, cross-room, wrong-author, and mismatched game/turn evidence MUST be rejected. A lobby line is public by construction, so the audience check does not apply to it; a report mixing lobby and room lines MUST be rejected (R-LCHAT-05). These are the **cited** lines; R-MOD-13 adds the lines around them. |
| **R-MOD-13** | A report MUST carry the conversation around what it cites, because a line on its own is often unreadable: the **server** copies up to **10 lines before and 5 after** the latest cited line, within **12 hours** of it, from the same room instance or the lobby, by anyone — but only lines the reporter received: a room line by R-MOD-04's stored audience, a lobby line by re-applying the reporter's blocks (R-LCHAT-03), since a lobby row records no recipients and a muted author's text must not reach the reporter through a report they can export — and never a cited line twice. | **R-MOD-21** | A report's evidence is read from `room_messages`, which is written in batches after a short linger (#972), so both report paths MUST **flush that queue before the read** — otherwise a line cited the moment it was said is not there yet. The flush MUST be bounded (2 s) so a database that has stopped answering cannot hold a report up; past it the report is filed with what is there. It MUST wait for the lines queued when it was called and no others, and MUST NOT hold a database connection or a lock while it waits: the writer needs a connection to make the progress the report is waiting for, and a report that waits while holding one starves the writer whose rows are its own evidence. | **R-MOD-05** | One reporter MUST hold **one open report per target**, where both the reporter and the target are the person: an account and every guest identity merged into it through `identity_aliases`, so a complaint filed against or by a guest is not filed a second time once that guest has claimed an account. Once decided, the same reporter may raise a new one — that is a new incident, not the same complaint repeated. [`services/player_reports.py`](../backend/app/services/player_reports.py) |
| **R-MOD-06** | Reporting MUST require an account, because a report a moderator cannot follow up on helps nobody. |
| **R-MOD-07** | Review MUST be one-way: a pending report receives one resolution and cannot later be silently rewritten. A decision covering a whole **Incident** (R-MOD-16) does not weaken this — each report it covers still records its own reviewer, moment and audit entry — but it MUST be atomic: the reports are locked as a set before anything is written, so an incident is never left half decided. |
| **R-MOD-16** | Reports of one incident MUST be shown and decided **together**. R-MOD-05 stops one reporter repeating themselves; it does not stop five people describing the same thing, which is what a room full of witnesses looks like and which read one at a time costs five readings of one story and four decisions about something already dealt with. An **Incident** is `(reported account, scope, room instance)` over pending reports, **derived** from what the report records rather than matched by hand or assembled by a moderator: a room instance says where the complaint happened and, ending when the room does, roughly when — without a window anybody has to pick a number for. Every lobby report about one account shares one bucket, the lobby having no instance to name; a report that cited nothing names no place to look and MUST stand alone. Prompt-content reports about one target group the same way. [`services/incidents.py`](../backend/app/services/incidents.py), [`api/moderation.py`](../backend/app/api/moderation.py) |
| **R-MOD-20** | A reporter MUST be told that a report of theirs was **reviewed**, because reporting into silence is what teaches people not to report. It is a **count of their own** decided reports and nothing more: not the outcome, not the target, not when. What was decided belongs to the reported player, and an outcome handed back to whoever asked about them would make a report a way of finding things out about somebody — which is a worse failure than saying nothing. It MUST be said **once**, recorded on the report itself, or it greets the reporter on every visit forever. The reading MUST be read-only and the recording MUST name **exactly the reports the message was about**. Recording before showing loses the message whenever the render does not happen — the account signs out while the request is in flight, the effect is torn down — and a report recorded as told that nobody was told about is never announced again. Recording *everything decided* at the moment of the acknowledgement has the same effect on a report decided between the two calls. So the read names what it counted, the message is shown, and the acknowledgement takes back that list; every condition MUST be re-checked on the write, the list being a client's account of what it displayed rather than authority over any row. The failure left is being thanked twice, which is the right one to be left with. It MUST NOT interrupt: a report decided days ago is worth knowing and is not worth stopping a game for. [`api/moderation.py`](../backend/app/api/moderation.py), [`ReportsReviewedNotice.tsx`](../frontend/src/components/ReportsReviewedNotice.tsx) |
| **R-FRIEND-14** | Being told a request was **accepted** MUST NOT depend on the client having watched it happen. The asker is then never told, on that visit or any later one. So *accepted and not yet announced* MUST be a fact on the friendship, told from the row, and MUST be recorded as told only **after** the message naming it was shown and for **exactly** what it named: recording first loses the news whenever the render does not happen, and recording everything outstanding swallows an acceptance that landed in between. The failure left is being told twice. An **arrival** MAY stay a diff, because an unannounced request is still sitting in the list under its badge, while an acceptance leaves nothing behind. [`services/friends.py`](../backend/app/services/friends.py), [`store/friendsStore.ts`](../frontend/src/store/friendsStore.ts) |
| **R-RULES-01** | The service MUST publish the rules it enforces, on a page reachable **without having been reported** — from the account menu, and from account creation, where the expectation belongs before anybody plays rather than after they are told they broke one. One page with anchored sections: there are six rules, and a contents page over three short sections would be a click in front of almost nothing. |
| **R-RULES-02** | Every **category** a decision can record (R-MOD-19) MUST have a rule anchored at it, and a notice naming a category MUST link there. A decision whose rule a player can read is one they can check; a category on its own is a second sentence to guess at. The rule's id **is** the category, so the two cannot drift — and because neither compiler checks that, a test MUST assert that every reason has a rule and that no rule anchors nothing decidable. |
| **R-RULES-03** | The rules MUST live in the repository, one typed module per locale, reviewed like code. | **R-MOD-17** | One decision MUST cover the whole incident: one step-up, one note, one action, and no report left pending about something already decided. The incident's reports MUST be locked **in id order and never starting from the report the request named**, because two moderators reaching one incident from two different member reports would otherwise take the same rows in opposite orders; the loser MUST get the refusal a slow retry gets. The lock MUST be what a decision is checked against, so the unlocked read that finds the key is never what it acts on. |
| **R-MOD-08** | Submitted context MUST be preserved as **reporter-supplied evidence**, and MUST NOT be treated as a server-verified fact merely because it was stored. |
| **R-MOD-08a** | Message retention MUST NOT sit on the delivery path. A message's identifier is issued before its row is written, so live chat never waits for the database; a report naming a message that was never retained MUST be refused as unavailable rather than accepted without its evidence. Retention that cannot keep up MUST withhold the identifier rather than delay the message or grow without bound. |
| **R-MOD-09** | Player-authored prompt content MUST have a separate, target-specific report flow against a list or an exact prompt version. Official bundled content, inaccessible content — any list that is not published — and self-reports MUST be rejected. |
| **R-MOD-10** | Prompt-content moderation MUST be **post-moderation**: a report alone never changes availability. Resolution explicitly chooses Active or Hidden; a dismissal MUST NOT mutate content. One decision hides or leaves up the content **once** and closes every complaint about it (R-MOD-16, R-MOD-17): the content is one thing, so deciding the reports one at a time would leave the rest asking about something already settled. |
| **R-MOD-11** | Hidden prompts MUST be filtered from future selection. Owners see moderation state in *My prompt lists*, and editing MUST NOT silently override a moderator decision. |
| **R-MOD-12** | A moderator MUST have a consequence between dismissal and **Suspension**: a formal **Warning** shown to the reported player once, in their own reported words — and, when the reports carried them, their own drawings (R-MOD-14), for the same reason — restricting nothing. Its acknowledgement MUST be recorded, and it follows the same role boundaries and same-report rule as a suspension. |
| **R-MOD-14** | A report filed from a room about the player **drawing** MUST be able to carry the canvas as it stood when the report was sent, because an offensive drawing is undone, cleared, or drawn over long before a moderator looks, and the turn's own stored drawing is its final state, written only when the game ends and erased with the drawer's account. The reporter asks for it (`includeDrawing`) and never supplies it: the **server** copies its own canvas frame, and only when the reported seat holds the pen this turn in a phase where the canvas still shows it (drawing, turn results) — a report about a guesser, or one sent once the next drawer is choosing, is accepted without it and the acknowledgement says so, since the turn can end under an open dialog. The copy MUST be kept for as long as the report is, under the stored-drawing rules (format named, checksum verified on read, the same size bound), and MUST be shown to a moderator drawn rather than described, with the prompt the drawer was given. The bytes MUST be readable only by a reviewer; the reporter's export records that a drawing was attached and of which turn, never the bytes. The client MUST offer the option only where the server would copy, and the server's rule is the one that holds. | **R-MOD-15** | Decided cases MUST stay reachable. The open queues are small and may be held whole; closed cases accumulate for as long as the service runs, so they MUST be served as one stream across player and content reports, **newest decision first**, under a bounded page (`limit` ≤ 100, `offset` ≤ 1000) that says whether an older page exists — a fixed window from the oldest end, which is what the queue's own ordering gives, would make the newest decisions the ones a moderator could never reach. The page MUST count **decisions, not reports**: an incident five people reported is one closed entry as it was one queue entry, and a pile-on must not be able to swallow a page. Grouping here MUST key on `decision_group_id` and **MUST NOT** reuse the open incident key — two incidents in one room instance decided a week apart are two entries, and that key would merge them. The key MUST be time-ordered (UUIDv7, minted when the decision is taken) so a page is an ordered index walk that stops when it has enough groups, rather than an aggregate over every report ever decided. A closed case MUST show what its open one did, evidence and drawing included, plus the **decision**: what was done, in one word read from the warning or suspension that names the report or the state a content decision set rather than from the report's own status, who decided it — the name resolved when read, never stored beside the case (R-AUDIT-02) — when, and the note. The list MUST carry the outcome beside each closed case so a queue can be scanned. A window at least 1500px wide MUST also keep the newest decisions in a column beside the case, whatever queue is open, because what was just decided is the context for the next decision (#581); opening one moves to the Closed queue rather than showing a closed case beside an open queue. ### Suspensions

| # | Requirement |
| --- | --- |
| **R-BAN-01** | Moderators and administrators MUST be able to create temporary or permanent suspensions. Moderators MUST NOT suspend peers; administrators MUST NOT be targeted. |
| **R-BAN-02** | Creating a suspension MUST revoke every signed-in device and remove any live room seat immediately. Ending an account — suspended or deleted — MUST close every **socket** it holds, not only the ones found holding a seat: an entry awaiting the database has no seat to find and would seat itself after the sweep had passed. Because closing a socket waits at that socket's seating gate, an entry holding it MUST also refuse to seat an account the sweep has reached — and MUST give back a seat it had already taken when the sweep reaches the account mid-entry, rather than leaving it to the reconnect grace. The sweep MUST mark the account's sockets before its own first await, since every step of it yields. Login, authenticated HTTP requests, and Socket.IO handshakes MUST all reject an active suspension. |
| **R-BAN-03** | A token revoked at ban time MUST stay recognizable until expiry, so its next request cannot be mistaken for a new cookieless guest. |
| **R-BAN-04** | **Data export, account deletion, and logout MUST remain available** through that ban-time credential — moderation MUST NOT erase privacy rights. |
| **R-BAN-05** | A suspension MAY carry an end date (24 h / 7 d / 30 d / none) and one with an end date MUST lift itself, because the list reports what is in force rather than trusting something to have run. Permanent MUST NOT be the default. |
| **R-BAN-06** | A suspension lifted by hand MUST keep its row and record who lifted it and why. Suspending from a report MUST resolve that report — acting on a report is deciding it. |
| **R-BAN-07** | A suspended player MUST be told before being signed out. Mid-game they hear it on the socket; otherwise from the first refused request, which carries the reason and end date rather than only saying no. |
| **R-BAN-08** | When decided from a report, the notice MUST show the messages the **decision** was about — the cited lines of every report it covered (R-MOD-17), deduplicated and in the order they were said, their own words as they were when the reports were made — and the drawings those reports carried (R-MOD-14): their own work, for the same reason. Reading the whole decision rather than only the report the ban names is what stops the notice depending on which complaint a moderator happened to click, and it cannot widen what is shown beyond the player's own: every cited line is authored by them by construction, and the context copied *around* those lines stays a reviewer's (R-MOD-12). The bytes reach a suspended account over `GET /api/suspension/drawings/{report_id}`, the one path beside R-BAN-04's that the ban-time credential may use, and the report named MUST be one the decision covered. **A ban naming a report about somebody else MUST be refused**, so a suspension cannot be used to show one player another's messages; the incident key contains the reported account, so this holds of the group as it does of the row. |

## 8. Privacy and data rights

| # | Requirement |
| --- | --- |
| **R-PRIV-01** | Every guest or registered player MUST be able to request a private, versioned JSON export of their own data. |
| **R-PRIV-02** | The export MUST NOT contain password or session hashes, other players' profile fields, or other players' message or guess bodies. It includes a reporter's own report text and submitted evidence — and, for a drawing attached under R-MOD-14, that one was attached and of which turn — never the bytes, which are the reported player's work kept for a moderator, and never the prompt, which a guesser reporting mid-turn has not earned — but excludes the reported account ID, reviewer identity, and internal resolution note. |
| **R-PRIV-03** | Export jobs MUST be stored **before** work begins, so a crash leaves a retryable row — and the row is the queue: one supervised in-process loop MUST build jobs **one at a time**, woken by the request and sweeping on an interval, and that sweep is also the retry. A row left `processing` by a process that died is reclaimed once it is 15 minutes stale; a planned shutdown MUST hand a claimed row back to `pending` rather than make the next process wait that out. One at a time because one worker (N-01) means a build's working set is every player's latency, so what has to be bounded is how much one build holds and that there is only ever one; a separate worker process or an external queue is N-12. Format v1 exports expire after seven days, and only the owning account may read any of those records. |
| **R-PRIV-04** | Deletion MUST require the current password for a registered account and an explicit confirmation in the UI. Guests may delete without a password, because possession of the HttpOnly session is their only credential. |
| **R-PRIV-05** | Deletion MUST leave the stable anonymized row, scores, prompts, and shared game structure intact, so **another player's history is never damaged.** |
| **R-PRIV-06** | Deletion MUST NOT invent or silently decrement a server-wide gameplay observation. Prompt usage facts contain no user identifier and stay reconcilable with retained anonymized outcomes. |
| **R-PRIV-16** | Every retention sweep MUST be bounded per run (rows per batch, rows per run, seconds per run), MUST delete in committed batches of deterministically ordered keys, MUST run from a supervised loop on a real clock with a bounded first pass at startup rather than an unbounded startup purge, MUST be fault-isolated from the sweeps after it, MUST report the rows actually removed, batches, duration and remaining backlog, and MUST NOT run inside any request or message-write transaction. A run cut short by its budget MUST be rescheduled sooner than the next interval. [`services/sweeps.py`](../backend/app/services/sweeps.py), [`auth/retention.py`](../backend/app/auth/retention.py) |
| **R-PRIV-17** | Every retained table MUST have a stated **deletion SLA** — how long a row may remain *after* becoming eligible for removal, which is a lag allowance on top of the retention window and not the window itself — together with its exemptions stated in the same place, and every sweep MUST measure and export what it left: the age of the oldest non-exempt row still eligible, the backlog behind it (counted to a cap), rows removed, budget exhaustion, duration and per-table failure. The measurement MUST use the sweep's own eligibility predicate, so nothing a policy exempts — a suspended account's sessions, a pinned prompt revision, a persistent room code, pending mail — is ever counted as lateness; a table that owes nothing MUST report zero rather than nothing, because an absent series cannot be alerted on. An exempt row MUST also be absent from the **candidates**, not merely from the count: a sweep that selects its oldest rows first and keeps re-selecting ones it can never act on starves everything behind them while reporting success on every run. A table past its SLA MUST raise an operator alert naming that table. Reason: a supervised loop that never fails proves only that something ran — a sweep removing five thousand rows an hour from a table growing by six thousand is healthy by every signal that existed before this. [`auth/retention.py`](../backend/app/auth/retention.py), [`slo.md`](slo.md) SLO-10, [`database.md`](database.md) §10 |
| **R-PRIV-07** | Retained message text MUST expire after 30 days. There MUST NOT be a transcript or profile-history endpoint. After 30 days the raw strings deliberately cannot be replayed through a new matcher; durable per-seat and per-turn counts still support difficulty and attempt analysis, and that bounded loss is the accepted tradeoff. |
| **R-PRIV-08** | Historical names, colors, and guest/registered state MUST remain as other players saw them. Ordinary profile edits MUST NOT rewrite them. Username and avatar are not rendered by finished-game history and MUST NOT be copied into it. |
| **R-PRIV-09** | Avatars MUST NOT hotlink arbitrary third-party URLs; only the content address of a picture this deployment stores, or the name of one of its own doodles, may be recorded, and either is served from this origin (R-AVA-03, R-AVA-09). |
| **R-PRIV-10** | Anonymous retention MUST be based on `last_active_at` — deliberately separate from page-load/login time and ordinary profile writes — MUST be bounded per run, MUST preview by default, and MUST record aggregate audit evidence when applied. A removal MUST select its candidates under a row lock that skips identities another write holds (`FOR UPDATE SKIP LOCKED`, ascending activity order) and MUST repeat every eligibility predicate on the delete itself, reporting only the rows actually removed, so a guest claimed, merged, seated or written into a finished game between selection and deletion is kept; a preview MUST take no lock. [`auth/retention.py`](../backend/app/auth/retention.py) |
| **R-PRIV-12** | Export requests MUST be spaced: at most one per account per **7 days**, never two live at once, and a **failed** build MUST NOT count. Building an export walks every game the account ever played, so an account with thousands of them is a real cost, and R-PRIV-01's right to a copy is not a right to a fresh copy on every click. The rule MUST be enforced where the job is written, so a second way in cannot be given a weaker one, and "never two live" MUST be held by the database — a unique index on one `pending`/`processing` job per account — because two requests arriving together can each read "nothing live" and only a constraint sees them at once; a refusal MUST say **when** the next request is accepted (`429`, `Retry-After`, and `nextRequestAt` on the listing), so the interface can disable the control and name the date rather than offer a request that will be refused. |
| **R-PRIV-11** | A stale guest's session MUST be removed with the account, so an old cookie provisions a new guest rather than resurrecting retained data. |
| **R-PRIV-13** | One export document MUST be bounded **while it is written**, not after: the builder MUST page the account's history rather than hold it, MUST count the JSON bytes as they go, and MUST refuse past `EXPORT_MAX_BYTES` (default 64 MiB before compression) by failing the job as `too_large` with no document stored — a refusal the status names, so the interface can say the size is the reason rather than a fault. The ceiling is the deployment's to raise, and a failed build does not count against the week (R-PRIV-12), so the right to a copy (R-PRIV-01) is met by raising it rather than by building at any size. Reason: a document built whole is one process's memory (N-01), the same reasoning as R-BUG-12, and a size that is a real cost for a heavy account is an unbounded one for an abusive account. |
| **R-PRIV-15** | Every writer of account-owned content — the message retention queue, the finished-game write and its retries, avatar, list and report writes — MUST re-read the account's lifecycle inside its own transaction under a shared, id-ordered row lock, and MUST drop or tombstone what an erased account authored, because a deletion can only erase what is already stored and a write composed before it would otherwise put the erased name, text or pixels back. Game facts stay (R-PRIV-05); the deletion and the writer end in the same state whichever commits first. Both MUST resolve a merged guest to its account before locking and lock the whole identity set in one ordered statement, so neither can hold what the other waits for; a write that loses a lock wait or a deadlock MUST be retried a bounded number of times before the game is recorded as unrecorded. [`auth/erasure.py`](../backend/app/auth/erasure.py), [`database.md`](database.md) §11 |
| **R-PRIV-14** | The stored document MUST be served by this origin to the owning session and MUST NOT be reachable through a bearer URL. It MUST NOT be held whole or compressed twice on the way out: a client that accepts gzip is handed the stored bytes as they are, one that does not gets them decompressed a chunk at a time, and either answer declares its length. The HttpOnly session is the stronger credential: a signed link in a URL travels through history, referrers and logs for no gain while the bytes live where the session already is. Should artifacts ever move to object storage — declined for now (N-18) — a short-lived signed download is that design's to make, not a stronger version of this one. |

## 9. Durability and history

| # | Requirement |
| --- | --- |
| **R-HIST-01** | Each live game MUST receive a stable UUIDv7 when it starts, reused by the history row and the prompt-usage batch. |
| **R-HIST-02** | Retrying the same ID **with the same content** MUST be idempotent, even if collection order changed. Reusing an ID for **different** content MUST raise an operator-visible conflict rather than duplicating or silently replacing history. The content includes the drawings — their bytes, or the reason one was not kept — and the prompt-usage batch keeps a digest of its own, so a retry carrying different drawing bytes or different usage facts is a conflict, not a silent accept (#541). | **R-HIST-03** | The finished-game write MUST be **all-or-nothing** in one transaction, and the one write a room waits on MUST run after every client-visible emit, so nothing a player is waiting to see sits behind a database round trip. | **R-HIST-26** | A finished or abandoned game MUST be written down whole — history, drawings, and prompt usage, as one versioned, bounded, checksummed envelope row — before anything tries to unpack it into history, and that row MUST be the queue: one supervised loop claims one row at a time with a lease and a fencing token, writes the two parts under the one row so a crash between them resumes only the missing one, and deletes the row on success. ### Runtime tuning

| # | Requirement |
| --- | --- |
| **R-CONF-01** | Values that decide how the running game *feels* MUST be changeable by an administrator without a deploy, and without a restart wherever the value is reached through an object rather than baked into one. The motivating case is a cadence no benchmark settles: the byte curve says to raise the drawer's flush interval and looking at a viewer's screen says otherwise, and the tolerance is far tighter than the numbers suggest. |
| **R-CONF-02** | Every tunable MUST carry its compiled default, its bounds, its unit and a one-line description of what it trades off, and the endpoint MUST serve all of them — so the panel needs to know nothing about any particular setting, and adding one does not mean editing the page. |
| **R-CONF-03** | Every value MUST be bounded **server-side**. The bounds MUST refuse a value the rest of the system could not live with, including pairs that are individually legal and jointly impossible: a client cadence and the budget that admits it are one setting wearing two hats. |
| **R-CONF-04** | A change carrying several settings MUST be validated as a set and applied as a set. Applying them one at a time would leave a refused request half-committed to a configuration nobody chose, and would measure each value against the ones not yet moved. Changes MUST also be serialized against **each other**: validation reads the values in force and the write is several awaits later, so two requests that each pass alone can otherwise land together on a pair the bounds exist to refuse. |
| **R-CONF-05** | Changes MUST survive a restart, MUST be adopted **before** the process admits players, and MUST fall back to the compiled default when unset. Whether a stored override **exists** MUST be tracked separately from whether its value happens to equal the boot value: inferring one from the other hides a row rather than removing it, leaves no way to clear it, and lets it win again the next time the environment moves. A reset MUST therefore remove the row even when nothing numeric changes. One unusable stored value MUST NOT prevent startup or cost the others — a release that tightens a bound leaves an old number behind it, and the answer is that value at its default plus a line in the log. Such a row MUST remain visible and clearable rather than being forgotten: an override the panel calls absent is one no reset can reach, and one that returns to force the day a later release widens that bound. |
| **R-CONF-06** | Every change MUST append an audit event naming the administrator, the setting, and the values moved from and to, **in the same transaction as the change itself**. Taking a durable override away MUST be recorded too, even when no number moves: how the deployment starts has changed. Only a submission that changes neither the value nor the override MUST be silent, or a panel posting its whole form buries the one change that was made. |
| **R-CONF-07** | Abuse backstops MUST NOT be tunable: the authentication and submission limits, and the canvas and replay ceilings. Nor MUST anything that can change a score, since every completed game freezes a rule snapshot. Nor MUST a value the frontend duplicates, which is a wire contract rather than a setting — including a *default* the client compiles in and always sends, since tuning that server-side changes nothing an ordinary player would see while the panel reports it as in force. Each value made tunable is one that can be set wrong in production. |
| **R-CONF-08** | A tunable is **not** a test setting. Client-side intervals MUST keep being fast-forwarded with the page's own clock (R-ENG-10) rather than made configurable, and the suite MUST NOT reach for the administrator surface to make itself faster. Configuring the *server* through the environment before it starts — as the E2E harness already does with `TURN_RESULTS_SECONDS` — is the boot value doing its documented job and is not what this forbids. |

## 12. Engineering constraints

| # | Requirement |
| --- | --- |
| **R-ENG-01** | `game.py` and `rooms.py` MUST stay pure logic with no sockets, covered by direct unit tests. |
| **R-ENG-02** | Client JSON commands MUST be validated as strict object payloads: values are not coerced, booleans are never accepted as integers, unknown fields are rejected, and **bounded validation completes before authorization or mutation.** |
| **R-ENG-03** | The binary drawing and fixed-array undo commands MUST have dedicated parsers for their documented wire formats. |
| **R-ENG-04** | The names the two sides share MUST be pinned by `test_wire_contract.py`, which also rejects wire names built from retired glossary vocabulary. |
| **R-ENG-05** | Malformed, unsupported, unauthorized, and out-of-phase drawing payloads MUST be rejected **before** being recorded or rebroadcast. |
| **R-ENG-06** | Extending a stored enum set MUST require one coordinated code, migration, contract, README, and glossary review. |
| **R-ENG-07** | Persisted timestamps MUST require timezone-aware inputs and normalize to aware UTC, so SQLite and PostgreSQL behave identically. |
| **R-ENG-08** | Entity IDs MUST NOT be used as capabilities. Session tokens, room codes, and invitation tokens stay independently random. |
| **R-ENG-09** | An E2E test MUST wait on the condition it actually cares about, never a fixed sleep sized to outlast it — and never `locator.count()`, which samples once and so asserts on whatever had rendered by that instant. `expect(locator).to_have_count(n)` and `locator.nth(n).wait_for()` retry; a count that loses the race fails as wrong data rather than as too early — such a sleep costs its full length on every run and silently stops covering anything when the thing it waits for gets slower. Where what is asserted is **transient** — a screen the game shows for a bounded phase, such as turn results — retrying is not enough, because the thing being retried for is removed while the retries run and every later attempt is answered by the screen that replaced it. Such a claim MUST be recorded in the page as it happens and asserted from the recording, so it is decided by page time rather than by how long the driver's round trips took (#724). |
| **R-ENG-10** | Where a test must sit out a production interval, it MUST fast-forward the page's own clock (`page.clock`) rather than spend the time, keeping the interval a production constant instead of something bent for the tests. |
| **R-ENG-11** | Benchmarks are **diagnostic baselines, not CI thresholds** — browser and machine timings vary. The database benchmarks MUST still *run* in CI, at their smallest size, so that one that no longer works is found by CI rather than by the next review (#895). |
| **R-ENG-12** | CI MUST run backend lint and tests, PostgreSQL migrations and **every database-backed test** against PostgreSQL, frontend test/lint/build, and multi-browser E2E. Database-backed, not the whole suite: a test that never opens a database — or that opens a SQLite file by name, as the concurrency suites deliberately do — runs there byte for byte as it ran on the SQLite job, which is three fifths of the suite and a third of that job's test time. What is selected MUST be derived from the import graph rather than a maintained list, so that a suite reaching for the shared fixture is included by doing so and cannot be left out silently; under-selection is the failure mode, and it MUST be asserted against the real tree. | **R-ENG-13** | CI MUST refuse a credential committed to the tree **or to any commit the change adds**, merge commits included — a value removed a commit later is burned just the same, the tree it leaves behind looks clean, and a value introduced only while resolving a conflict appears in no parent's diff at all. [`ci.yml`](../.github/workflows/ci.yml) |
| **R-ENG-14** | CI MUST fail on a known advisory in either Python manifest or in the frontend lockfile. Build and test dependencies count: they run in CI with a checkout before anything they touched reaches a player. |
| **R-ENG-15** | Coverage MUST be gated **per risk-critical module**, not only in total, and each module MUST carry **both** a statement floor and a **branch** floor. Per module, because a suite this size absorbs one module losing its tests without moving the total more than a rounding error. Both numbers, because either alone can be met by a suite that is not exercising the code: a statement measure marks an `if` covered the moment it is reached, and a branch measure is trivially met by a module with few branches. The gate MUST read `percent_statements_covered` and `percent_branches_covered` — **not** `percent_covered`, which under `--cov-branch` is a combined ratio reading far higher than branch coverage alone — and MUST refuse a report produced without branch measurement. | **R-ENG-16** | The live room's render regions MUST stay isolated: an update MUST NOT re-render a region with no interest in it. Insulating it means more than wrapping it in `memo`: an element built inline in the parent's JSX is a **new object on every parent render**, so a `memo` handed one can never hold, and the wrapper reads as protection while providing none. | **R-ENG-17** | A failed E2E run MUST keep the server's log and CI MUST upload it beside the JUnit report. ## 13. Explicit non-goals for v1

These are decisions, not gaps. Implementing one is a product change that needs its own
design, not a bug fix.

| # | Non-goal |
| --- | --- |
| **N-01** | **Multi-worker or horizontally scaled deployment.** Requires shared room/session/timer state and cross-worker Socket.IO delivery. |
| **N-02** | **Live-state snapshots or crash recovery of an active game.** Rooms, canvases, timers, and scores are never serialized. |
| **N-03** | **Ratings, seasons, achievements, competitive-mode eligibility, or server-wide standings.** The durable *foundation* exists; the policy does not, and MUST NOT be introduced as mutable counters or by rewriting finished games. |
| **N-04** | ~~**Community prompt-list discovery**, a favourite/star table, or a user-facing fork endpoint. `public` visibility is reserved.~~ **Withdrawn** — being built under R-LIST-11…R-LIST-18 (#398). It was declined because the reserved columns were the easy half and nobody had decided the hard half: who may publish, who reviews what they publish, and what a star is for. What changed the answer is that the hard half turned out to have a defensible small form — publication gated on the *account* rather than the content, moderation kept reactive on machinery that already exists, and an operator switch standing in for the approval queue that a single-operator deployment cannot staff (R-LIST-13). Two pieces of the original proposal did not survive the design and are not coming back through it: user-selectable `public` on an ordinary save (R-LIST-02), and free-text tags (R-LIST-18). |
| **N-05** | **A chat transcript or profile message-history endpoint.** |
| **N-06** | **Invitations to players who are not friends, and any notification that carries a room code.** An invitation between friends exists (R-FRIEND-06) and carries a token rather than a code; nothing else does. There is still no way to reach a stranger directly. |
| **N-07** | **External identity providers.** Schema is reserved; no provider-login API is enabled until identity-linking flows ship. Avatar uploads left this list with #573 (R-AVA-01…05) once validation, moderation and the export/deletion paths existed. |
| **N-08** | **A built-in room-preset catalogue or preset sharing.** |
| **N-09** | **Prompt languages beyond the Latin registry** (`en`, `de`, `es`, `fr`, `it`, `nl`, `pt`) until their matching semantics are implemented. |
| **N-10** | **A remote password-reset API.** There is no authentication that would make one safe; the server-side command exists instead. |
| **N-11** | **Server-side PNG rendering.** The server stores and replays actions, never pixels. |
| **N-13** | **A versioned REST API (`/api/v1`) or N/N−1 client support.** The client and the server are one same-origin deployment that changes together (R-PLAT-03, R-PLAT-09); a stale tab is reloaded onto the current build (R-CONN-09…11), never served an older contract. Supporting two contracts at once would need a second code path on both sides for a client that, by construction, does not exist for more than a reload. |
| **N-14** | **A room-state delta protocol.** `room_state` is broadcast whole on every change and stays that way. Measured on a real guest's stream under the full load population (#493, [`benchmarks/room_state_deltas.py`](../benchmarks/room_state_deltas.py)): replacing every snapshot after the first with a typed patch saves 1.5% of the stream on the wire (1.0 B/s per seat; 2.6% of the smaller stream after #869, still 1.0 B/s; 1.9% after epic #888, 0.7 B/s), because permessage-deflate with a 32 KB window already encodes each snapshot as a back-reference to the last — 63 B on the wire through real mixed traffic — and building one costs 4 µs. A patch protocol would add a revision-and-gap policy, a snapshot fallback and authoritative host/vote handling for that gain. Reopen only if the window shrinks or `room_state` grows past the window. That happened once, and was answered without a patch protocol (#871): the finished game's recap had pushed a 16-seat waiting-room snapshot to 47–138 KB, so each repeat cost 2–4 KB per seat; it now travels once (`game_ended`, `last_game`), the snapshot is 4.5 KB, and a repeat is 56 B again. |
| **N-15** | ~~**Phishing-resistant MFA (WebAuthn / passkeys).**~~ **Withdrawn** — shipped as R-AUTH-23 (#684). It was declined because a WebAuthn ceremony costs new backend dependencies against a set that is deliberately argon2 plus the SQLAlchemy stack, and because the mitigations around a code — single use even inside its own step, step-up per destructive action, week-long staff sessions — narrow the relay window. What changed the answer is that they only narrow it: a code read aloud is still spendable by whoever hears it, and no arrangement of codes fixes that. The dependency cost was also larger than recorded here (six packages, not three) and was paid anyway. Staff-only, as N-15 assumed; whether a player may hold a passkey is open under R-AUTH-23 rather than decided. |
| **N-16** | **An exhaustive breached-password corpus.** `weak_passwords.txt` is a few hundred entries, not the eight hundred million a range API would reach, and this is a consequence of the 12-character floor rather than a shortfall: published top-100k corpora are overwhelmingly 8–10 characters, so naming them would refuse nothing R-AUTH-19's length rule refuses first. What survives a length rule is *shapes* — a short password written twice, a word with a year on it, a keyboard row walked to its end — and those are patterns, which the screening covers generatively. A password that is genuinely breached, twelve characters long, and matches no pattern will pass. Accepted: the alternative is an outbound dependency on every registration, a fail-open decision, and a request made because of somebody's password. |
| **N-19** | **Enforcing the AFK check against a modified client.** The check is a question the client answers, so a client that always answers is never marked. Making it adversarial would need a periodic activity report — the heartbeat traffic R-AFK-02 exists to avoid — or a server-side inference from input the server cannot see, and it would still be defeated by a script. The population it would catch is people cheating to keep a seat they are not using, against whom the **AFK vote** and the **Kick vote** already work and are cheaper. Reopen if a seat-release policy is built on top of the flag, where the incentive to game it would be real. |
| **N-17** | **Adaptive or reputation-based login throttling.** The three buckets in R-RATE-12 are fixed ceilings. A global limit that tightened the per-address ceiling automatically while the failure rate was elevated would be better under an active attack, and is not built: it is a shared, self-adjusting number that is hard to reason about and harder to test deterministically. The deployment-wide bucket is deliberately the blunt version — it refuses only callers already carrying failures of their own, so saturating it costs an attacker their own access rather than everybody's, and it is not a way to lock a deployment out. |
| **N-12** | **A separate worker process or an external queue for deferred work.** Mail, account exports, retention and metrics are supervised loops in the one application worker (N-01, and the #456 risk acceptance), with a database table as the queue wherever the work has to survive a restart. |
| **N-20** | **Article, plural and gender tolerance in guess matching.** A German answer is stored as `Hund` rather than `der Hund` (R-PROMPT-10), so the article a player types is an alias question, not a matcher one; accepting inflections generally would mean a per-language morphology the seven languages do not share, and every rule that accepts more also accepts a wrong guess more often. A wrong guess scoring a point is worse than a right one being rejected, and the near-miss hint already tells a player they are close. Reopen if a language is added whose written form makes the bare noun unnatural, or if near misses show players losing turns to inflection rather than to spelling. |
| **N-18** | **Object storage for drawings, exports, screenshots and pictures.** #471 measured what the blobs cost before choosing, rather than assuming they had to move: a drawing is 67 KB of database per finished game and the only blob with no expiry, read back in 1.4 ms, and moving it would neither reduce the retained bytes nor survive the all-or-nothing finished-game write (R-HIST-03, R-HIST-26) without staged upload, manifest publication, orphan reconciliation and deletion tombstones. The seam is kept — `turn_drawings.object_key` beside `payload`, pictures already content-addressed (R-AVA-03) — and the refusal is conditional, not permanent: `turn_drawings` past 50 GB, or a restore breaching #458's RTO, reopens it (R-OBS-14). The measurements and the reasoning are in [`database.md`](database.md) under *Storing the drawings*. |

## 14. Interface language

| ID | Requirement |
| --- | --- |
| **R-I18N-01** | Prose a **player** reads MUST be written where the reader's language is known, which is the client. The server MUST name *what happened* — an enumerated code plus typed parameters — and MUST NOT compose the sentence. The one exception is **email**, which has no client at the other end. This is not a style rule: an interface cannot be translated while half its sentences are written by a process that does not know who is reading, and every refusal a player could see would have to travel through a second translation mechanism on the server. The server MAY still send English prose (`error` on an acknowledgement, `detail` on a response) and no client may render it — it exists for a log line, for an operator reading a response by hand, and for the bug report a player attaches to a complaint, all of which are read in one language. **Staff and operator surfaces are deliberately outside this rule**: the moderation queue, the operations pages and every audit record stay English, because an audit trail that reads differently depending on who opened it is worse than one that is always the same. [`app/refusals.py`](../backend/app/refusals.py), [`lib/refusals.ts`](../frontend/src/lib/refusals.ts) |
| **R-I18N-08** | **Email is the one place the server writes prose for a player**, because there is no client at the other end to write it — and therefore the only place the reader's language is **stored** rather than resolved. The locale MUST be **frozen onto the outbox row when the message is queued**, never read at send time: the outbox is a durable queue swept by a loop, a send can happen hours later, and resolving late would let a preference changed in between re-language a message that was already composed — including the one about the security event that prompted the change. A recipient with no locale of their own MUST be written to in English, and so MUST a language this build does not speak: a message they can probably read beats none. Every clause MUST be built inside the locale — a suspension's *"It lifts on …"* and *"recorded as …"* are its own words, not English fragments handed over to drop into a sentence (R-I18N-02). Dates in mail MUST be written **ISO**: a month name needs a locale database this project deliberately does not carry, and a date nobody can misread beats one that is charming in English and wrong in six other languages. [`auth/mail_copy.py`](../backend/app/auth/mail_copy.py), [`auth/mail.py`](../backend/app/auth/mail.py) |
| **R-I18N-07** | A language MUST be **offered only when its catalogue is complete**: the list of locales a player can pick is derived from the catalogues rather than declared beside them, so a language cannot be offered before somebody has finished writing it. Completeness is the compiler's rule; **quality is a separate promise and MUST NOT be conflated with it.** The six non-English locales are machine-drafted, and every entry a native reader has confirmed is recorded per locale, with the unreviewed count reported in CI — printed rather than asserted, because a build that is honestly labelled a draft should not fail. **A locale reaching zero unreviewed entries is a launch gate**, not a build gate, and belongs to a person; it is the same shape `#691` used for prompt content, and for the same reason. A translated locale MUST also be *translated*: a test fails when a large share of one locale's longer sentences are still the English words, which is what a draft that stopped early looks like from outside. [`content/ui/reviewed.ts`](../frontend/src/content/ui/reviewed.ts), [`tests/localeReview.test.mjs`](../frontend/tests/localeReview.test.mjs) |
| **R-I18N-06** | The **interface locale** MUST resolve in one order — the account's stored setting, this browser's remembered choice, `Accept-Language`, then English — first match wins, with no merging, because a merge of two languages is not a language. It MUST be resolved **before the first paint**: a page that renders in English and then switches has already shown the wrong language to whoever reads slowest. The first paint therefore waits for the account's answer — bounded, so a slow or absent server costs a moment rather than the page, and past the bound the browser's order stands ([`lib/startup.ts`](../frontend/src/lib/startup.ts)). Only the resolved locale's catalogue MUST be downloaded — every locale but English is a chunk of its own, fetched alongside the account read inside the same bound — because each visitor paying for six languages they will not read was 35% of the entry bundle (#982). A catalogue that cannot be fetched MUST leave the page in English rather than blank, and MUST NOT overwrite the reader's remembered choice, since the failure is the network's and not their decision ([`content/ui/index.ts`](../frontend/src/content/ui/index.ts)). It MUST be changeable from the **lobby** as well as from Settings, at every width: the lobby is where somebody who cannot read the language they landed in arrives, and Settings is one more screen to find in it ([`InterfaceLanguageButton`](../frontend/src/components/InterfaceLanguageButton.tsx)). It MUST be stored per account, since a browser describes a device rather than a person, and MUST be remembered in the browser as well, which is all a guest has. It MUST be **distinct from the room's prompt language** (R-PROMPT-02) and carried in its own column and its own registry: a Dutch speaker playing an English room is ordinary, and the two are bound by different things — a prompt language needs matching semantics to exist at all (N-09), an interface locale needs only somebody to have written the words — so the sets may diverge. `<html lang>` MUST follow it, because it is what a screen reader picks a voice from and what a browser offers to translate. The locale decides date and number **conventions** and the **Time format** setting decides the hour convention on top of it; neither overrides the other. [`lib/interfaceLocale.ts`](../frontend/src/lib/interfaceLocale.ts), [`api/user_settings.py`](../backend/app/api/user_settings.py) |
| **R-I18N-04** | Every word the interface says MUST live in a **typed catalogue**, one module per locale, and a locale MUST define **every** key: offering a language and finishing it are the same act, because a page that falls back mid-sentence is worse than one that is honestly in another language. Completeness is a **build rule** — the English module is the reference type and every other locale is declared against it, so a missing or invented key fails `tsc` rather than review. Entries with values MUST be **functions**, not format strings: parameters and plurals are then checked by the compiler, there is no runtime message parser to ship or to escape, and a locale writes the plural categories its own language has via `Intl.PluralRules` rather than the two English happens to need. | **R-I18N-05** | A player-facing component MUST NOT hold a sentence of its own: text between tags, the attributes a screen reader speaks, the arguments of the calls that put words on screen, and the words a component keeps out of its markup - a table of labels, a branch picking one of two, a fallback, a returned sentence, a word a template composes (`${n} players`) or a hand-rolled `n === 1 ?` plural - all come from the catalogue. | **R-I18N-03** | A **room-authored announcement** (`R-BLOCK-03`'s term) MUST be one payload reaching every seat, carrying an enumerated code and typed parameters rather than a sentence, and each client MUST render it for its own reader.
